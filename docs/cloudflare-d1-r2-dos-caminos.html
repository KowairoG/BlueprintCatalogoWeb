Llevar el catálogo a Cloudflare: los dos caminos y lo que costaría

D1 para los datos, R2 para las fotos. Comparación honesta entre el despliegue “todo Cloudflare” y el conservador, con precios reales confirmados en la documentación oficial.

Preparado para el proyecto idk_sell_a_software · Datos verificados en developers.cloudflare.com el 26 de agosto de 2026 · Precios en USD.

Tu catálogo ya está construido sobre SQLite con Prisma (chubby.db), con las fotos guardadas como archivos y referenciadas por URL en ProductoImagen. Eso te deja en la mejor posición posible: D1 es SQLite por dentro, así que la base de datos casi no cambia, y las fotos tienen su hogar natural en R2. La pregunta real no es “¿D1 sí o no?” — es dónde va a correr tu Next.js. En eso se dividen los dos caminos.

La idea en una línea Datos estructurados (productos, categorías, existencias) → D1. Imágenes y archivos → R2 (en la base solo guardas la URL). Lo único que cambia entre los dos caminos es si tu app corre dentro de Cloudflare Workers o sigue corriendo como servidor Node donde ya la tienes.

Camino A — Todo Cloudflare

Recomendado a mediano plazo

Next.js corriendo dentro de Workers (vía OpenNext) + D1 + R2. Es el despliegue “de verdad”: dominio propio, sin túnel, y aprovechando el free tier al máximo de forma sostenible.

Cómo se hace, en orden

  1. Adaptar Next para Workers con @opennextjs/cloudflare. Este adaptador toma el build de Next y lo transforma para que corra en Workers usando el runtime de Node. Soporta App Router, SSR e ISR — que es justo lo que usa Chubby.
  2. Crear la base D1 y apuntar Prisma a ella con el driver adapter oficial de Prisma para D1. Tu schema.prisma se queda prácticamente igual (sigue siendo provider = "sqlite" en la práctica); cambia la forma de conectarse, no el modelo.
  3. Migrar el schema y los datos. Corrés tus migraciones contra D1 y cargás el seed (datos-iniciales.ts). Los datos de chubby.db se exportan e importan una sola vez.
  4. Crear el bucket R2, subir las 20 fotos de fotos-chubby/, y reescribir la columna ProductoImagen.url para que apunte a R2. Un script de una sola pasada.
  5. Configurar los bindings (D1 y R2) en wrangler y desplegar. La app le habla a la base por binding, sin cadena de conexión ni contraseñas.

A favor

  • Free tier al máximo y sostenible; te quitás el túnel cloudflared.
  • Migración de datos mínima: SQLite → SQLite.
  • Lecturas rápidas cerca del usuario; escala sola sin administrar servidor.
  • Una sola factura y un solo panel para todo.

El costo real

  • El trabajo está en migrar el runtime, no la base: ajustar lo que asuma Node completo.
  • Límite de tamaño del Worker: 3 MiB comprimido en Free, 10 MiB en Paid. Una app Next puede acercarse — a veces empuja al plan de $5.
  • Estás en Windows: OpenNext recomienda WSL/Linux para el build. No es opcional tenerlo cómodo.
  • Node Middleware (Next 15.2+) todavía no está soportado.

Camino B — Conservador

Para avanzar hoy sin reescribir el despliegue

Seguís corriendo Next como lo tenés (servidor Node + túnel cloudflared, o un VPS barato), y solo movés lo que da beneficio inmediato con el menor riesgo.

Cómo se hace

  1. Mover solo las imágenes a R2. Subís las fotos al bucket y reescribís ProductoImagen.url. Tu app las sirve desde R2 sin cambiar nada más. Este paso ya te da CDN global y egress gratis — es la mejor relación beneficio/esfuerzo de todo el documento.
  2. La base de datos, dos opciones: dejarla como chubby.db local (cero cambios), o pasarla a D1 usando su HTTP API desde tu servidor Node. La HTTP API funciona desde cualquier lado, pero cada consulta es una llamada de red, así que es más lenta que un binding — sirve para bajo volumen.
  3. Todo lo demás queda igual: mismo deploy, mismo túnel, misma operación. Cuando quieras, migrás al Camino A sin haber perdido nada.

A favor

  • Migración mínima; se hace en una tarde.
  • Ganás R2 (imágenes + egress gratis) sin tocar el runtime.
  • Cero riesgo sobre lo que ya funciona.

La contra

  • Seguís dependiendo de un servidor/túnel encendido (algo que administrar).
  • D1 por HTTP API es más lento que por binding.
  • No es el despliegue “final”; es un paso intermedio.
Recomendación Empezá por el paso 1 del Camino B (fotos a R2) esta semana — beneficio inmediato, riesgo cero. Y dejá el Camino A completo para cuando tengas un rato con calma y WSL listo. Tu proyecto ya está diseñado para SQLite y hasta pensado para clonarse a otras tiendas, así que el destino natural es el todo-Cloudflare.

Los respaldos ya vienen incluidos: Time Travel

D1 trae respaldo y recuperación punto-en-el-tiempo sin configurar nada. Se llama Time Travel: podés restaurar la base a cualquier minuto del pasado reciente. Está siempre activo, es automático y no cuesta nada extra.

PlanHistoria que podés recuperar
Workers Freeúltimos 7 días
Workers Paid ($5/mes)últimos 30 días
Qué te resuelve (y qué no) Time Travel te deja "volver al estado del martes" ante un borrado mal hecho o una corrupción — eso solo ya es un respaldo de verdad, no una simple copia. El matiz: vive dentro de tu cuenta de Cloudflare, así que no te cubre un desastre a nivel cuenta (cierre, facturación, o borrar la base entera con wrangler d1 delete). Para eso, la propia Cloudflare recomienda además exportar la base con wrangler d1 export a un bucket R2 cada tanto. Dos capas: Time Travel para el "deshacer" diario, export a R2 para el seguro contra perder el proveedor.

Fuente: D1 — Time Travel and backups (verificado el 26 ago 2026). La retención de 30 días aplica al plan Workers Paid; en el Free son 7 días.

Conclusión sobre el dinero Para el catálogo de Chubby, el free tier te alcanza hasta tener tráfico serio. Cuando lo despliegues “de verdad”, el costo realista es la base de $5/mes de Workers Paid, y solo un éxito grande te llevaría al rango de $15–$35/mes. Y sobre almacenar fotos: aunque guardaras miles de imágenes en alta, R2 cobra $0.015/GB-mes — 100 GB serían $1.50 al mes. El almacenamiento nunca va a ser tu problema.
